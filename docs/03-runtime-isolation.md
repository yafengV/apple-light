# 运行环境隔离

状态：用户要求转化的设计与验收草案。ShipiOS 自有本地配置与子进程环境已实现并测试；固定版本 Codex Core 的显式 home 与进程内临时认证已通过本地假服务验证，见 [Agent RPC 验证](190-codex-agent-rpc.md)。Skills、MCP、插件、跨进程锁及真实服务凭据链路尚未完成隔离验收，不能宣称完整隔离。

## 1. 隔离目标

ShipiOS 不依赖用户安装的 Codex，不自动导入其模型、登录、配置、Skills、MCP、插件或会话。两者可以同时运行；修改、退出登录或卸载一方不改变另一方状态。

这是**产品配置与状态隔离**，不是同一 macOS 用户下的操作系统级安全隔离。Xcode、系统 Keychain 服务、项目文件、网络、受管理设备策略仍属于共享环境。若还要求阻止进程任意读取用户目录，需要另行设计和验证沙箱。

## 2. 为什么不能只换 CODEX_HOME

官方文档说明本地状态通常位于 `CODEX_HOME`，但配置还可以来自项目、系统和受管理来源。因此独立 home 目录只是起点。[状态位置](https://learn.chatgpt.com/docs/config-file/config-advanced)、[配置分层](https://learn.chatgpt.com/docs/config-file/config-basic)

认证后端、Skills/插件发现、父目录指令、继承环境变量和启动 shell 也需逐项验证。不能将“独立目录”直接标为“完全隔离通过”。

## 3. 路径设计

```text
~/Library/Application Support/ShipiOS/
  config.toml                  产品用户配置，不含秘密
  Agent/                       适配层传入的独立运行时根目录
    sessions/
    skills/
    cache/
  State/shipios.sqlite          产品工作流与工件索引
  Artifacts/<run-id>/           日志、截图、结果包、报告
  Workspaces/<project-id>/      独立工作区

~/Library/Logs/ShipiOS/         脱敏诊断日志

<project>/.shipios/
  config.toml                  项目参数，不含凭据
  workflows/                   经支持的场景与流程定义
```

名称和目录是产品设计；并非要求 Codex 原生使用同名布局。adapter 负责映射。实际会话、缓存与认证文件由 P0 核查后记录。

## 4. 配置与策略分开

普通设置按以下优先级合并：运行参数 > 经信任的 `.shipios` 项目配置 > ShipiOS 用户配置 > 产品默认值。每项保留来源，便于诊断。

有效权限还必须受产品约束、用户授权与适用组织策略共同限制。更高优先级的模型或项目设置不能扩大权限。默认不自动读取个人 Codex 配置；若设备上的组织策略适用于 ShipiOS，遵守该约束或报告不兼容，不能把“隔离”实现成绕过管理策略。

项目指令与配置分开处理：是否采用仓库 `AGENTS.md`、父目录规则或共享 Skills 是独立选项。首次信任时展示来源；不因读取项目代码就默认执行其中 hooks 或自动启动 MCP。

## 5. 隔离矩阵

| 维度 | 设计要求 | 验收证据 |
| --- | --- | --- |
| 可执行文件 | 使用随产品分发的 helper，固定版本 | 不安装 Codex CLI 的机器仍可启动 |
| 用户配置 | 不自动读取 `~/.codex` | 修改其模型后 ShipiOS 有效配置不变 |
| 项目配置 | `.shipios` 独立解析；不自动合并 `.codex` | 放入冲突值后仍得到预期配置与来源 |
| 系统/管理配置 | 明确识别来源与适用性 | 测试环境验证冲突时遵守约束或清晰失败 |
| 认证 | 独立 Keychain service/account 或受控存储 | 两个测试账号登录/注销互不影响 |
| 模型 Provider | 端点、模型、凭据引用独立 | 两侧请求分别到达预期测试端点 |
| Skills/插件/hooks | 只发现批准的产品与项目来源 | 哨兵资源不被载入或执行 |
| MCP | 独立注册表与授权 | 用户 Codex 中的测试 server 不被启动 |
| 会话/历史/日志/缓存 | 独立目录和索引 | 运行产物只写入预期位置 |
| 环境变量 | 创建子进程时显式构造环境 | 外部测试密钥和端点不污染请求 |
| shell 启动 | 受控命令不用登录 shell 注入配置 | shell 启动文件中的哨兵不生效 |
| 更新/卸载 | 只操作 ShipiOS 资产 | 用户 Codex 配置与会话散列保持不变 |

## 6. 凭据和子进程

Keychain 命名空间可采用产品专属 service 前缀，具体 bundle ID 待命名后确定。模型凭据、ASC 凭据、Git 凭据独立作用域，配置只存引用。不能假定更改 `codex_home` 就更改了 Keychain namespace。

启动 Agent 时从最小环境构造 `PATH`、`HOME`、`TMPDIR`、语言和必要 Xcode 选择信息；保留真实 `HOME` 可能仍使其他工具发现用户设置，因此要逐个检查工具读取行为。代理、企业 CA 与自定义工具路径通过产品设置显式加入，不能简单一律删除而破坏环境。

模型密钥优先只交给模型连接模块；若适配器必须使用环境变量，则只给该进程注入。构建脚本、普通 shell 工具和模拟器进程不应继承模型或发布凭据。ASC 凭据只在发布步骤需要时提供。

本地执行不意味着所有数据都不出设备：代码片段、日志或截图可能被发往用户选择的模型服务。连接设置应说明数据用途；日志与导出报告默认脱敏。

## 7. P0 测试方法

使用临时用户目录、测试凭据和 fixture 创建两套冲突配置，不改写开发者真实 Codex 设置。记录测试前后文件散列、有效配置来源、测试端点收到的请求，以及文件/进程访问证据。

必须覆盖：个人 Codex 已安装/未安装、冲突配置、外部 `OPENAI_API_KEY`、父目录指令、Keychain 登录/注销、并行运行、模型切换、异常退出与升级迁移。MDM 等无法本地模拟的项目列为未覆盖，不宣称全部隔离已通过。

将测试结果逐项写为通过、失败或未覆盖。出现无法关闭的上游发现机制时，评估适配补丁或缩小兼容性承诺，再更新架构决策。
