# 文件选区模型编辑

参考：本机 Codex 分发资源 `text-file-editor-tab-content.electron-703b6088ed88.js`，SHA-256 `0abbe98e9b95a6f6f092b4993963f99052d5160db9fcdb5d0bafd6b6efb37a03`；可见的请求规则为纯文本替换、32 KiB 选区/结果、128 KiB 文档窗口、原位选区操作与 Edit/Reject/Accept 审阅控制。

文件页在可编辑文本选中非空、非纯空白的内容时，于选区旁显示“编辑选区…”入口。用户输入修改要求后，ShipiOS 使用当前任务的独立模型配置生成纯替换文本，保留首尾空白；Chat Completions 使用独立 API 请求，Responses 使用只读、纯文本、无 MCP 工具的临时 Codex Core 回合，完成后销毁临时线程。依照当前 Codex 本地参考实现，单次选区和模型替换结果上限均为 32 KiB，文档上下文窗口约 128 KiB；Responses 的长上下文通过临时文字附件进入同一回合。编辑后的文件目前仍受 ShipiOS 应用内 1 MiB 上限约束，这是与 Codex 参考实现仍存在的差异。

生成结果先显示原选区和建议替换文本，可返回修改要求重新生成。生成阶段不改草稿或磁盘；用户点击“接受修改”时才通过原生 `NSTextView` 应用替换，因此保留现有撤销与自动保存流程。“拒绝”或关闭面板不修改文件。接受前检查文件路径、完整文件字节、选区和编辑资格；文件或选区变化后旧建议无法应用。切换项目或文件时取消并清理选区编辑状态。

验证：29 项文件及选区相关测试通过，涵盖 UTF‑16 选区、空白保留、最大选区与上下文、无效/超大响应、建议阶段无写入、接受后的原生撤销、旧选区拒绝，以及本机 HTTP 夹具分别通过 Chat Completions 与真实 Codex Core Responses 传输。正式应用构建和严格深度签名检查通过。Codex 的审阅操作嵌在编辑器原位；ShipiOS 目前仍用文件页内审阅面板，尚未达到布局/焦点完全一致。Mac 锁屏阻挡前台鼠标焦点、窗口布局、可交互工作区及 Codex 双端配对；用户配置的真实服务端也尚未验收。本项不能计入 45 项完整页面交互验收。
