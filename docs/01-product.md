# 产品定义与范围

状态：产品草案。用户明确提出要做 iOS 开发上架一条龙软件，并指出产品必须具备 AI 修改代码的能力；以下阶段划分是整理建议。

## 1. 产品定位

**帮助已有 iOS 项目的开发者，把一次需求或发布任务变成经过验证、可以审查和交付的结果。**

长期愿景：需求 → AI 修改代码 → 构建 → 自动验证 → TestFlight → App Store → 审核反馈修复。

核心价值在于把 Coding Agent 接入真实 iOS 工程：理解项目与签名状态、执行验证、保留证据、控制失败重试，并明确何时可以进入下一阶段。AI 编码是产品能力之一，验证与交付闭环是差异化方向。

## 2. 首批用户与痛点

| 用户 | 待验证的痛点 | 最小价值证明 |
| --- | --- | --- |
| 有 Mac、已有项目的独立开发者 | AI 改完代码后仍需手动编译、操作模拟器、定位错误 | 在真实项目中减少人工验证与修复时间 |
| 多项目外包工作室 | 签名、截图、测试和发布步骤重复 | 同一流程可在第二个项目复用 |
| 小型 iOS 团队（讨论约 3–30 人） | AI 产出难纳入现有 PR、QA、CI 流程 | 输出可审查 diff 与可复现验证报告 |

首轮建议优先选择愿意提供真实项目的独立开发者或小团队。无 Mac、没有现成代码的新手属于后续市场；大型企业私有化需要单独验证采购与部署需求。

## 3. 两种 MVP 与本次建议

原对话出现两种切入点，用户尚未最终选择：

| 路线 | 最小闭环 | 主要风险 |
| --- | --- | --- |
| 开发验证优先 | 需求/Issue → 编码 → Simulator 验证 → PR | 需求理解和 UI 验证可靠性 |
| 发布优先 | 已有项目 → 检查/修复 → TestFlight → 提审 | 签名、账号权限、外部状态和发布差异 |

**整理建议：先实现共同基础，以开发验证闭环为首个可演示里程碑，再将发布闭环作为首个商业试点。** 这样保留用户要求的 AI Coding 能力，也不在最初同时承担完整需求开发、云服务和 App Store 自动发布。

## 4. 分阶段功能范围

| 能力 | M1：本地验证 | M2：发布试点 | 后续 |
| --- | --- | --- | --- |
| 导入已有本地 Git 项目、扫描环境 | 必须 | 完善兼容性 | 远程仓库接入 |
| 明确任务下的 AI 改码、构建失败修复 | 必须，范围受限 | 增加发布相关修复 | 复杂功能开发 |
| Xcode 构建、日志、结构化诊断 | 必须 | Archive/Export | 多 Runner |
| Simulator 启动、截图、冒烟场景 | 必须 | 发布前回归 | 通用自然语言 QA |
| diff、测试证据、人工接管 | 必须 | 关联发布版本 | 团队评审 |
| 本地交付报告 | 必须 | 关联 TestFlight | GitHub/GitLab PR |
| 签名检查 | 环境诊断，主要只读 | 发布配置检查 | 多账号管理 |
| Metadata、截图、审核风险报告 | 不进入首个闭环 | 必须支持草稿 | 多语言、审核知识库 |
| TestFlight 上传与状态查询 | 不进入首个闭环 | 必须 | 自动分组分发 |
| App Store 提交 | 不进入首个闭环 | 准备材料；提交单独授权 | 审核反馈修复闭环 |
| 云 Mac、SSO、团队权限 | 不包含 | 不包含 | 验证后安排 |

M1 建议先限定单个 App、可选择的 scheme、一个支持的模拟器环境与一条确定性场景。Xcode/macOS 最低版本、Intel 支持、SwiftUI/UIKit、SPM/CocoaPods/Tuist 的支持矩阵在 P0 后确定。

## 5. 首个端到端演示

示例任务：为联系人页面增加姓名搜索，并验证匹配与无结果两种状态。

1. 用户选择已有项目，查看 Xcode、scheme、依赖和 Git 状态；有多个候选时选择目标。
2. 输入任务与验收条件，选择已独立配置的模型。
3. 创建隔离工作区，保存基线，展示任务计划。
4. Agent 修改代码，工具层执行构建；失败时把诊断交回 Agent，最多进行有预算的修复轮次。
5. 在指定 Simulator 安装启动，执行已定义场景，保存结果与截图。
6. 展示 diff、验证状态、失败原因、消耗和证据。用户可以继续修改、人工接管或导出报告。

原始项目未提交修改必须可保留；不能默认只复制 HEAD 后声称验证了用户当前版本。基线选择及工作区策略见工作流文档。

## 6. 结果与验收

成功结果应包含：输入任务、代码基线与最终树标识、改动清单、构建命令摘要、退出状态、测试场景和断言、截图/日志引用、仍未覆盖的项目。

M1 退出条件：

- 在固定演示项目完成一次真实改码、构建和场景验证，并展示完整报告。
- 注入构建错误时可定位原因；修复不成功时明确停止并保留工作区。
- 未运行、受阻、失败和通过可区分；截图与模型判断不能单独冒充测试通过。
- 任务可取消；Agent 崩溃后可查看已持久化记录并按安全检查点恢复。
- 并行运行用户 Codex 时，ShipiOS 的配置、凭据和会话互不污染。

试点指标（目标待校准，不是已达成结果）：记录首次完成率、人工介入次数、构建/验证耗时、模型消耗、每任务支持工时。相同项目和任务建立人工基线后再比较收益。

## 7. 明确不承诺的能力

首版不承诺从一句话生成完整 App、后端和支付体系；不承诺任意第三方模型兼容、所有真机能力覆盖、自动通过 Apple 审核或固定“十分钟上架”。Push、CallKit、VoIP、Watch、后台行为等需真机验证的能力列入后续专项，不以 Simulator 结果替代。
