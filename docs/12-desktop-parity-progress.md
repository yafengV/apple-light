## 独立服务的使用方式

1. 打开 ShipiOS → 设置（⌘,）→ 模型与 API。
2. 填写服务商给出的基础地址（通常以 `/v1` 结尾）、模型 ID 与 API Key。
3. 保存配置，可先测试连接；回到任务，选择“模型会话”并发送消息。
4. 支持 `/chat`、`/doctor`、`/build`。普通文本按当前操作模式处理；诊断和构建仍由独立 Rust Agent 执行。

配置写入桌面数据根目录的 `model.json`，权限 0600。密钥不写入 JSON，使用 Keychain service `dev.shipios.desktop.model-api`，account 为配置的服务基础地址。不会导入 `~/.codex` 或环境中的 API Key。配置地址要求 HTTPS；允许本机 loopback HTTP。请求不跟随重定向，错误提示不回显服务端原始响应正文。

用户已决定自行填写已有服务，因此没有申请新 Key，也没有读取或替用户配置真实凭据。本轮使用本机 mock 服务验证应用流程。**真实服务、模型支持、配额和真实密钥存取，等待用户填写后验证。**

## 架构状态

本轮 `ModelAPIClient` 是 Swift 客户端内的独立文本会话适配层；它没有链接 `codex-core`，不能执行自主编码。原先确认的 `codex-core + extension-api → shipios-agent` 架构目标保持不变，后续需要将模型会话与工具事件迁入独立 Agent，并补协议、沙箱和审批。UI 中明确显示现阶段能力，不将普通 Chat API 包装成完整 Codex Agent。

## 验证证据

使用 macOS 原生 `.app`，没有用 iOS Simulator 验证桌面界面。测试 API 数据目录是 `.shipios-local/parity-qa`，与原开发工作区 `.shipios-local/desktop` 分离。

- `./script/test.sh`：Rust fmt、Clippy、12 项 Rust 测试、19 项 Swift 测试、真实 Agent IPC 冒烟通过。日志 `.cache/parity-full-tests.log`。
- Swift 增加：旧工作区迁移、队列持久化与任务隔离、草稿保护、路径穿越/符号链接/二进制拒绝、Git 暂存/取消暂存/重命名解析、字面路径参数、stdout/stderr 分离、被父仓库忽略的目录浏览。
- 网络测试启动仅监听 `127.0.0.1` 的 Python fixture：中文 SSE、GET /models、HTTP 错误、损坏帧、提前断流、取消与部分输出、重定向拒绝均通过。没有访问收费模型服务。
- 原生窗口：⌘K 命令面板 → 筛选“终端” → Enter，实际打开 PTY；执行 `printf` 与 `pwd`，输出标记和正确项目目录。
- 原生窗口：设置保存 fixture 地址/模型 → 连接测试显示 1 个模型 → 聊天显示 `Hello 世界!`。
- 原生窗口：流式回复时追加消息 → ⌘. 停止 → 部分回复保留且队列仍在 → 队列菜单“立即发送”成功回复。重启后历史与取消状态仍在。
- 原生窗口：⌘⇧B 打开浏览器，访问 fixture 的 `/v1/models`，WKWebView 显示 JSON 页面。

实机发现的额外问题：Git 子进程的 stderr 不能混入 porcelain 文件列表；临时目录/符号链接路径必须标准化；Git 不应沿项目目录向上扫描父仓库；SwiftTerm 资源包和许可证必须一起打包。均已对应修复。

最终实机复查：⌘P 能找到被父仓库忽略的 HelloShipiOS 示例文件，筛选并回车后显示完整 Swift 源码和文件标签；文件树包含可展开工程目录。在 `/tmp/shipios-parity-git-20260916` 独立测试仓库中，审查页显示真实新增行，点击暂存后可在“已暂存”看到文件；提交后列表为空，命令行核对提交标题为 `Validate native Git commit flow`，工作树干净。没有在主仓库执行暂存或提交。

最终完整回归再次通过：12 项 Rust、19 项 Swift、IPC 冒烟。测试 HTTP 服务已停止，App 恢复到原开发工作区；mock 模型配置只保留在隔离测试目录中。
