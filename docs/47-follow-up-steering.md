# 追加消息：引导当前运行与等待下一轮

2026-09-17。依据官方 General 设置中的 Follow-up behavior，ShipiOS 在主窗口“设置 → 通用”加入“引导当前运行 / 等待下一轮”。设置没有独立窗口；进入后仍是原 `AppContentView` 主窗口，返回按钮和 Esc 回到原任务。

## 实现语义

- **等待下一轮**是兼容旧版本的默认值。追加消息持久化到当前任务队列，当前回复成功结束后按顺序发送；停止、失败或重启不会丢失队列。
- **引导当前运行**先持久化追加消息，再取消当前独立 API 流，将已经收到的部分回答写入会话历史，并立即以该历史继续新请求。
- 如果任务已有等待消息，引导消息插到该任务队列的最前面。引导完成后继续处理原有队列。
- 自然完成与取消同时发生时，以队列消息 ID 判定归属；已被自然完成路径取走的消息不会重复发送。
- 文本、图片、文件和审查评论沿用同一持久化提交路径。下一次请求配置失败时消息仍留在队列。

独立 OpenAI 兼容 Chat Completions 服务不能把新文本注入已经建立的 HTTP 流。因此这里的“引导”是取消并继续请求，界面说明明确显示这一语义。它保留用户可见的部分回答与上下文，但不能声称底层协议和 Codex Runtime 的同回合 steering 完全相同。

## 自动验证

真实本机流式服务测试覆盖：

1. 旧 `workspace.json` 默认迁移为“等待下一轮”，新设置可编码、恢复。
2. 原队列行为继续自动发送，取消后保留消息和部分回答。
3. “引导”取消慢速流，新请求收到 `system → user → partial assistant → user` 的真实历史。
4. 已有排队消息时，引导消息先运行，原消息随后运行；三个执行状态为 `cancelled → succeeded → succeeded`。

定向测试 5 项通过。完整 `./script/test.sh` 通过：Rust fmt、Clippy、12 项 Rust 测试、278 项 macOS Swift 测试以及真实 IPC 冒烟，零失败。

## 原生界面验证

隔离数据目录下构建、签名并启动 `ShipiOS.app` 后实际完成：

1. 从新任务页点击齿轮，原窗口标题切换为“设置”，没有创建设置窗口。
2. 通用页显示两个分段选项；切到“引导当前运行”后说明改为“停止当前模型请求，并将已生成的部分回答作为上下文立即继续”。
3. 在主窗口“模型与 API”配置本机 fixture 服务并成功测试连接。
4. 发送慢速流式请求，在回复过程中输入 `context`；输入区按钮显示“引导当前运行”及相同帮助文本。
5. 点击后，第一条回复显示“回复已停止，已保留收到的内容”，随后出现 `context` 回合。fixture 返回的请求历史实际包含第一条的部分回答。
