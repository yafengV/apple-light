# 分离 HEAD 的 PR 新分支流程

## 参考范围

本阶段重新读取当前安装的公开应用资源：版本 `26.911.61220`、构建 `9647`。`git-action-new-branch-field-d7fd686030a3.js` 与 `local-conversation-git-actions-61fd0d6dad47.js` 均与已有分析副本逐字节相同，SHA-256 前缀分别为 `43af88eb6f2f48e5`、`9f8d7ac696ebff22`。没有读取用户账户、认证或会话资料。

PR 弹层的 `Wt` 导入实际对应 `Kn`：当前分支查询成功且结果为 null 时要求新分支。新分支建议使用分支前缀与会话标题，约 200 毫秒后检查本地重名；动作传递新分支名，先生成内容，再创建分支，随后按所选路径提交、推送和创建或浏览器预填。分支字段的普通 Return 保持编辑，Cmd+Return 激活动作，输入法组合保持原生处理。

进一步核对 `ti` 与公开 worker 的 `Qpe`/`t3`：普通 `worktree` 模式先创建本地引用，前端接着执行检出；`synced` 模式另写托管分支信息。本阶段实际检出新分支，托管同步元数据仍需单独对齐。

需要纠正此前文档的默认分支推断：普通本地仓库在命名的默认分支上不能直接创建 PR；托管工作树有独立的分支准备流程。后续继续跟踪入口调用链，确认命令/摘要入口隐藏而审查工具栏保留禁用创建项，详见[第 381 篇](381-pull-request-entry-readiness.md)。本阶段实现分离 HEAD 弹层内的新分支路径，不把默认分支直接新建 PR 视作参考要求；托管分支准备仍需分别对齐。

## 实现

PR 检查在允许本地准备时可读取分离 HEAD 的仓库、远端、源提交和默认分支，普通独立推送仍要求命名分支。默认分支只用于分离状态的元数据快照，流程另行捕获新分支的远端目标、跟踪引用与预期提交；不会把快照的默认分支当作推送目标。

分离状态的弹层标题栏显示“新分支”，表单增加新分支字段、建议名称、初始焦点和防抖校验。后台流程重新检查名称、来源 HEAD、文件/索引、远端与目标提交。生成上下文及浏览器比较地址使用拟建分支；字段被修改、生成取消、名称重名或授权失效时不能继续旧操作。

勾选本地变更时，在来源提交创建分支后提交选中内容并推送；已有新提交且没有待提交内容时只创建并推送。取消勾选时仍创建并发布源提交，但不暂存或提交工作文件；没有相对目标的新提交则在创建分支前拒绝。推送失败后保留已经成功的分支和提交，重新检查实际命名分支，重试继续推送而不重复提交。

直接创建和草稿沿用第 378 篇的表单重置与所属任务 PR 记录；浏览器预填沿用输入保留规则，不把浏览器表单记作已创建 PR。

## 验证

首组 13 项定向测试通过，日志 `.cache/pr-new-branch-focused.log`。补充来源 HEAD 变化、新远端目标变化和 force-with-lease 目标校验后，最终 107 项相关 Swift 回归全部通过，零失败、无跳过，耗时 2012.372 秒，日志 `.cache/pr-new-branch-regression.log`。包含 8 项分支、25 项 PR、12 项弹层/键盘、52 项串联流程和 10 项推送；首组 13 项已包含其中，不重复相加。新增 16 项用例取得通过证据。

已验证清洁分离提交的直接创建、草稿与所属任务记录，默认提交上的本地变更新分支，取消勾选时保留暂存/未暂存/未跟踪内容，浏览器预填不记录虚构 PR，推送失败保留分支并继续原提交。来源 HEAD/新目标变化、手改分支、重名/无效名称、生成取消和权限撤销均阻止旧操作；普通独立推送仍拒绝分离 HEAD。两种模型协议及既有弹层生命周期规则通过相关回归。

最终仅补齐标题栏静态文案后，通过 `script/build_and_run.sh --build-app` 正式应用构建，Swift 构建耗时 7.36 秒，日志 `.cache/pr-new-branch-app-build.log`；严格深度签名校验通过，日志 `.cache/pr-new-branch-signature.log`。仅构建，没有启动新应用或确认原生工作区可交互。

所有仓库、推送目标和 GitHub CLI 都使用本地临时夹具；协议回归使用 loopback 模型服务及实际 Core/Agent，不访问真实账户、收费模型服务或创建真实远端 PR。
