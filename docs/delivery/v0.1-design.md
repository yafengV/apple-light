# ShipiOS 首版本地开发交付方案

本方案把持续扩大的 Codex 对齐工作收敛为 **ShipiOS v0.1：可验收的本地 AI 开发版**。终点是用户能通过独立 API 完成一次真实改码、构建和测试、差异审查与本地提交，并能使用固定清单中的核心页面和交互。完成这批验收后结束目标任务，后续需求另立版本。

制定日期：2026-10-10。盘点起点：`902ca2ca`，另有未提交的环境设置焦点修复及前台测试改动。本方案、[验收标准](v0.1-acceptance.md)、[任务看板](v0.1-tasks.md)共同组成当前交付依据；旧路线和数百篇阶段报告保留为历史证据，不再驱动新增任务。

## 1. 产品目标与边界

面向已有本地 iOS 工程的开发者，解决“模型改完代码后，无法确认是否能运行、改了什么、如何安全交付”的问题。沿用[原产品定义](../01-product.md)的开发验证优先路线；TestFlight、App Store 和商业试点属于后续版本。

首版交付四件东西：可运行的原生 macOS 应用及独立 Agent；一条真实模型开发闭环；核心 UI 验收记录；绑定候选版本的本地交付报告与使用说明。这里的版本只保证本次记录的开发 Mac、macOS、Xcode、模拟器设备及所配置服务组合；包声明的 macOS 14 最低版本不等于已经完成全部系统和硬件兼容性认证。

### 固定的功能范围

| 范围 | 首版必须可用 | 不扩展到 |
| --- | --- | --- |
| 独立 API 与会话 | 设置服务、选择实际可用模型、流式发送、停止、引导、重试、续聊、错误恢复 | ChatGPT 账户、订阅、组织和官方专属模型档位 |
| Core 工具 | 真实代码修改、命令与构建；审批、提问、计划；本地 skills 与 MCP 的配置和调用 | 在线市场、所有 OAuth、当前 Core 没有的协议能力 |
| 项目与历史 | 导入、切换、侧栏、Activity、搜索、归档恢复、草稿和冷启动恢复 | 云同步、远程主机、云工作区 |
| 分支与工作树 | 固定历史边界的本地分支、新 Git 工作树、准备状态、取消重试、脏文件保护、项目环境 | 跨主机／跨提交 Handoff、任意复杂迁移 |
| 输入与时间线 | 中文输入、粘贴附件、常用键盘、模型能力显示、工具与审批卡片、滚动跟随 | 语音、听写、宠物、跨应用 Computer Use |
| 开发工具 | 文件保存冲突处理、查找与选区建议、PTY、diff、Git 本地提交与受控推送 | 所有托管平台的 PR 等价、自动 PR 值守和合并 |
| 内容与窗口 | 标签、分屏、基础浏览器、固定与重命名、拖放、独立任务窗口、关闭与恢复 | Chromium 特殊媒体和高级开发协议、所有浮窗变体 |
| 主窗口设置 | 下表固定设置组的导航、修改、保存取消、搜索、键盘和持久化 | 所有官方账户页、云自动化、未支持的高级设置 |

已有可选功能不因本次规划直接删除；已展示入口必须正确说明可用性，不能假装成功、点击无反应或无限等待。可选模块影响核心流程或引起现有回归失败时仍需诊断和处理，但不因此增加一套完整可选功能验收。

### 固定的页面与设置组

核心页面为：新聊天／聊天时间线、项目侧栏、Activity／搜索／归档、分支和工作树准备页、文件编辑器、终端、差异审查／Git、浏览器／内容标签／分屏、独立任务窗口、主窗口内设置及共用确认弹层。相同控件的验收优先复用，不把每个菜单变体都扩为一项新目标。

设置分成六个验收组，组内页面逐页记录结果：

| 组 | 包含页面 | 代表操作 |
| --- | --- | --- |
| S1 | 通用、外观、个性化 | 修改一个可用偏好，取消一次、保存一次、重启核对 |
| S2 | API／Agent | 配置独立服务、模型和运行策略；校验错误与未保存保护 |
| S3 | Git／审查、项目环境 | 改分支前缀／审查偏好；环境编辑、保存、放弃和返回焦点 |
| S4 | 快捷键、通知 | 录制／取消绑定；改变通知时机；核心导航与通知目标正确 |
| S5 | 本地 MCP、skills | 启停本地服务和权限；发现并调用本地技能；来源隔离 |
| S6 | 工作树、归档、基础浏览器 | 验证现有相关设置入口、可用性及实际行为；没有独立设置页时记录入口位置，不新造页面 |

## 2. 设计方案

### 用户主流程

1. 在主窗口设置中填写已有 API 服务，保存并选择其可用模型；凭据不进入聊天、仓库和报告。
2. 导入本地项目，显示 Git 和 Xcode 环境，确认工作目录与改动基线。
3. 创建任务，输入明确需求和验收条件；时间线展示实际运行、工具、审批和错误。
4. Agent 修改隔离工程，执行构建与测试；失败有命令、诊断和重试入口，用户可停止或接管。
5. 在工作台查看 diff、测试与运行证据；人工检查后做本地提交。推送验收只使用隔离的本地裸仓库。
6. 关闭并重启应用，恢复正确项目、会话与草稿，继续输入；失败恢复状态不能永久停留在 loading。

首个固定演示使用 `fixtures/HelloShipiOS` 的隔离副本：让真实模型新增计数器，初始显示 `0`，点击两次加一后显示 `2`，点击重置回到 `0`。先准备固定 UI 断言和失败夹具，再让模型改产品代码；当前 fixture 尚无 UI 测试 target，这属于 T03 的明确工作，不把现有截图当作测试通过。

**ShipiOS 自身是 macOS 应用，必须在实际 Mac 窗口验收。** Simulator 只用于它所开发的 iOS 演示工程。两者的构建、版本和证据分别记录。

### 架构选择

保留当前 SwiftUI + 少量 AppKit 客户端，独立 Rust `shipios-agent`，通过版本化 stdio JSON-RPC 通信；复用已有状态、事件、工件存储和 `shipios-codex` 适配层，不重写整个产品。

当前仓库通过 `vendor/codex-core` 嵌入 Core，相关上游依赖固定在 `50d77959bf927293c4b5ddcca81d05331ae582ea`。v0.1 不为追随桌面 App 升级 Core；缺少能力时先确认接口事实，再明确禁用可选入口。SwiftUI 负责页面和可见状态，AppKit 只补窗口、原生输入、菜单与焦点；客户端不能用乐观显示代替 Agent 的真实结果。

API、配置、认证、会话、skills／MCP 继续使用 ShipiOS 独立路径与来源规则。任务、窗口、项目和异步请求都校验归属，旧回调不能抢回页面或修改其他任务。草稿、脏文件、未保存关闭必须提供明确的保存／放弃／继续编辑结果。

### UI 对齐的设计基准

参考锁定为仓库已记录的 Codex **26.930.51102 / build 13100** 公共资源和已有交互证据，不追踪每次官方更新。共用核心页面对齐导航位置、主要布局、控件含义、状态、键盘和焦点。设置在主窗口内打开；API／运行时等 ShipiOS 自有页面沿用相同导航与控件规则。

对齐记录按“参考行为 → ShipiOS 行为 → 差异 → 验收结果”保存。允许 macOS 原生字体、材质、渲染的细小差别；不允许主操作位置错误、关键内容遮挡、状态含义不同、丢焦点、键盘无法继续、草稿丢失或错误任务导航。不以全像素相等或全部 47 类页面作为门槛。

现有 Codex 前台读取未获授权，不重试或绕过。只使用已经允许的仓库参考资料；参考不足的项目标注“参考待核实”，先定义产品行为，不能冒称已经完成双端实测对齐。

### 页面结构与交互状态

主工作区沿用侧栏项目／聊天导航、顶部任务与内容操作、聊天时间线和底部输入框；文件、终端、审查与浏览器通过内容标签进入分屏或完整视图。切换布局保留内容实例和草稿，回到聊天恢复输入焦点；独立任务窗口只有显式打开时才创建。

进入设置时，在**同一个主窗口**展示设置导航与内容，返回恢复来源任务、布局与焦点。确认、重命名和未保存提示使用归属当前窗口的弹层或原生 sheet，不创建独立设置窗口。搜索结果直接定位具体设置，无法使用的选项明确说明原因。

每条异步流程明确区分空态、准备中、运行中、成功、失败、取消和外部阻塞。等待要有阶段与停止／取消入口；失败要有原因和重试；保存成功必须反映实际持久化结果；草稿保护提供保存、放弃、继续编辑三种可理解结果。错误不能只靠日志显示，后台完成不能抢回用户正在操作的页面。

## 3. 验收与完成条件

交付只看[固定 32 项验收](v0.1-acceptance.md)，不看阶段文档数量或历史测试总数。每项分别记录代码实现、自动验证和实际交互证据；需要实际窗口的项目不能靠隐藏窗口通过，真实服务闭环不能靠受控 HTTP fixture 通过。

完成条件：全部必需项在最终候选版本有有效证据；最新完整回归没有未解释的失败；无阻断首版流程的 P0／P1 缺陷；操作说明和交付报告齐备；所有完成阶段提交推送；磁盘预算检查通过。外部依赖未满足时记录阻塞，不能将整版标为完成。

本轮规划不宣布 UI 已完全对齐。目前旧目标为空，没有运行中的目标；环境设置焦点改动未提交、最终前台验收未运行，关联测试仍有失败。这些作为新计划的起始事实，不能被规划文档抹成已完成。

## 4. 排期与执行控制

[任务看板](v0.1-tasks.md)分为 T00–T11，T00 为本次规划，其余包含独立开发与测试步骤。先 T01 盘点，再 T02 收尾已开始的修复，随后优先真实开发闭环，再完成其他固定页面，最后整版回归。一次只有一项开发任务在进行，不并行堆积未验证代码。

初始估算为 T01–T11 合计 **44–79 个有效工作小时**，按每天 8 小时约 **6–10 个工作日**。这是尚未完成新基线盘点的规划估算，不是自动任务连续在线时长或交付承诺；Mac 解锁、API 配置和其他外部等待另记，模型与工具调试也可能改变估算。T01/T02 结束依据实际缺口校准一次，给出每项剩余估算和原因，不把截止日期每天顺延。

每项到达估算上限仍未通过时，停止扩展该项，报告失败证据、已耗有效时间和剩余缺口；在看板中标明估算失效和修订依据。核心缺陷继续按原验收修复，可选完善移入后续版本；需要扩大交付范围时先明确变更及工期影响，再取得用户决定。

每个已验证的独立阶段检查变更范围、提交并推送。每次进度报告只写当前任务、实际完成的验收 ID、剩余失败／依赖和下一步，不把“又通过若干测试”当作交付进度。到终点立即结束该目标，不自动追加新功能。
