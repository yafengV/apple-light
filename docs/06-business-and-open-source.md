# 商业与开源策略

状态：来自讨论的商业假设与整理建议，尚无客户访谈、销售或付费留存数据。本文件中的价格不是市场报价或已确定售价。

## 1. 商业价值假设

用户可能愿意为减少重复验证、缩短发布准备时间、定位签名/构建问题和降低人工交接成本付费。需要用真实任务验证节省的时间与支持成本，不能从竞品存在直接推导 ShipiOS 的付费意愿。

讨论中提出的五层产品可共享同一基础：iOS 开发交付工具、AI QA、审核辅助、公开 Skills、企业自动化服务。首阶段保持一个产品主线，避免同时运营五个独立产品。

## 2. 早期商业模式

建议先本地运行、用户自备模型凭据，收费对象是工作流、验证与交付能力。用户订阅账号能否用于第三方产品登录，需要单独核对服务条款和实际集成能力；不预设所有 Codex/Claude 订阅都可直接复用。

先选择一个明确付费场景做试点，例如“已有项目完成稳定的 TestFlight 发布”或“每次 AI 改码后自动冒烟验证”。咨询接入服务可以补充现金流，但应记录每个客户的定制工时，避免工具化目标被持续定制替代。

云 Mac、存储和协作控制面在确认需求后增加，届时另行计量资源成本。

## 4. 成本与计费边界

每次运行记录模型用量（供应商可提供时）、耗时、修复次数、Mac 运行时间、工件存储和支持工时。费用不可得时显示未知，不估算成精确账单。

贡献收益的评估口径：实际收入 − 平台承担的模型/计算/存储成本 − 支付费用 − 可归因支持成本。用户自付模型费用不计为 ShipiOS 收入或支出，但会影响总使用成本和转化。

正式计费前定义免费额度、取消任务、平台失败、用户环境失败、重试、退款和超额资源边界。首版避免“无限用”承诺。

## 5. 开源策略草案

用户询问了是否开源，但尚未确认方案。讨论建议是 Open Core；下表是可讨论边界，不是当前许可证授予。

| 能力 | 候选边界 |
| --- | --- |
| 项目分析、构建工具、本地 Runner、基础 Simulator 操作 | 倾向开源 |
| 基础检查、通用 iOS Skills、工具 schema | 倾向开源，逐项核对来源与许可 |
| 核心调度、基础取消/恢复/授权、用户查看自身日志 | 建议作为基础产品能力，不依赖付费才能保证安全可用 |
| 高级 QA 场景管理、审核诊断策略与持续维护 | 可做商业增强 |
| 团队权限、多级审批、集中审计、云 Runner、企业管理 | 候选商业模块 |
| macOS 客户端 | 对话未定案，需要单独决策 |

“基础 Simulator”与“高级 AI QA”、“基础事件日志”与“组织级审计”应明确区分，避免免费与付费范围互相矛盾。

不在此次整理中直接添加 LICENSE。Codex 主仓库标示 Apache-2.0，但分发 ShipiOS 前仍需整理所用依赖、修改、NOTICE 与第三方资产清单。[Codex LICENSE](https://github.com/openai/codex/blob/main/LICENSE)

客户代码、截图、审核反馈不默认成为公开案例库。复用失败案例需获得授权并去除客户数据与凭据。知识积累来自经许可的数据和可重复验证的策略。

## 6. 首批客户验证

建议目标：先访谈约 10 位目标开发者，从中寻找 3–5 个愿意提供项目的试点；这些是工作目标，不是已有客户。

访谈围绕最近一次真实任务：卡在哪里、耗时多久、用过什么工具、谁负责发布、是否允许发送代码到模型、何时愿意付费。通过现场演示或授权试用记录干预次数与实际节省时间。

获客素材围绕一条真实闭环：构建失败→修复→Simulator 场景→可审查报告。候选渠道包括现有开发者关系、GitHub、技术文章和 iOS 社区；先验证试用与付费，再扩大传播。Star 和安装数作为触达指标，不代替活跃或收入。
