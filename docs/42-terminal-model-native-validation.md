## 终端实测

在原工作区 `.shipios-local/desktop` 中，使用本轮新建的终端会话验证：

- Cmd+J 打开终端并接受键盘输入；执行静态 `printf` 标记，截图确认实际输出。
- 终端聚焦时 Cmd+, 打开同一主窗口设置；在快捷键搜索框输入 `browser` 正常筛选，隐藏终端没有收到该输入。
- Esc 返回后原草稿仍在，焦点回到消息输入，终端输出保留。
- 切换到另一任务显示独立 Shell，切回原任务仍保留原终端输出。
- 点击结束保留输出并显示“会话已结束”；重新打开获得新 Shell 和键盘焦点；执行 `exit 7` 后显示“已结束 · 退出码 7”。

本轮没有验证所有终端文本选择、复制、缩放、全部快捷键或跨应用重启恢复。终端在辅助功能树中主要表现为滚动控件，因此使用原生截图与实际命令输出交叉验证，未将 AX 控件名称当作完整终端内容。

## 模型弹层实测

原用户尚未配置 API；Ctrl+Shift+M 正确打开主窗口“模型与 API”设置。随后使用隔离数据目录 `.cache/model-ui-46b8nulx` 和仅监听本机的测试模型服务，验证已配置状态：

- 弹层打开后搜索框获得焦点，服务返回 `fixture-model`，当前自定义模型也保留在列表中。
- 方向键和 Return 选择模型，弹层关闭，输入区模型名称更新，焦点回到消息输入。
- Esc 关闭弹层后恢复消息输入焦点。
- 搜索无匹配时显示空状态和手动 ID 入口，Return 可选择 `manual-ui-model`。
- 推理强度设为“高”，由弹层进入主窗口 API 设置，模型 ID 和推理强度保持一致；Esc 返回工作区。
- 停止本机服务后重新打开弹层，显示连接错误，同时保留当前模型、手动 ID 能力和推理强度。

这些测试没有使用真实密钥、调用外部模型或更改原用户的模型配置。本机服务已停止，应用已恢复原工作区、原任务和未发送草稿。

## 启动期间命令问题与修复

隔离测试启动时，工作区恢复中的内容控件已经禁用，但应用菜单快捷键仍可触发模型命令，提前进入空的 API 设置页。统一在 `commandEnabled` 中检查 `restoringLibrary`，使菜单与内容控件的恢复状态一致。

新测试在恢复状态下逐个检查全部命令，确认它们不会改变页面或打开弹层；恢复结束后，模型入口重新可用。该保护不改变系统退出应用等原生菜单行为。

这次较长的恢复等待由本机诊断定位：线程停在读取测试 `model.json` 的文件打开调用，TCC 日志同时显示 `kTCCServiceSystemPolicyDesktopFolder` 授权等待。系统状态随后变化，应用恢复完成。本轮没有操作系统授权按钮或修改隐私保护；不将这次等待错误归因于模型网络，也没有通过该修复宣称消除系统授权等待。
