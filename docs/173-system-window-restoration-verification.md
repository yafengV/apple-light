# 系统窗口恢复与跨任务标签归属验收

2026-09-25。在第 172 篇实现基础上补原生验收。本轮没有修改产品代码；验证结果不支持为应用强制重开所有窗口。

## 启动条件

SwiftUI 任务 `WindowGroup` 保持默认系统恢复策略。第 146 篇已有普通启动不恢复窗口、进程级开启恢复后成功的记录；第 172 篇普通启动只出现主窗口，不能据此单独确认产品缺陷。

本轮使用 `script/build_and_run.sh --app --data-root /tmp/shipios-window-restore-20260925 -NSQuitAlwaysKeepsWindows YES`，只给隔离测试进程启用恢复。没有写入系统全局或应用持久偏好。每轮通过应用的退出快捷键正常退出，再通过项目脚本启动。

## 已通过的原生流程

1. 建立 A、B 两个独立窗口。A 为聊天/审查、右侧网页和底部终端，右侧宽度 400、底部高度 255，保留未提交地址编辑；B 为单独的网页标签和任务草稿。退出前最小化 A。
2. 重启后 B 自动显示已保存网页，网页输入可用，切回聊天仍是 B 草稿。最小化 B 后，从主窗口点击固定网页唤回 A：A 的三类标签、尺寸、地址编辑和草稿均恢复。A 网页实际输入 `A auto restored`，终端执行并输出 `SYSTEM_RESTORED:18428`。该固定入口只唤回已注册的原独立窗口，本轮没有手动新建 A 窗口。
3. 在 A 所属窗口内通过命令菜单导航到 B；此窗口的 B 起初没有内容标签，未误用 B 原窗口布局。新增网址以 `?window=A-task=B` 区分，B 原窗口保存的是 `?window=B`。
4. 再次正常退出重启，活动窗口自动显示 `?window=A-task=B`。本地 HTTP 服务在同一启动时段收到两个不同 B 网址的请求，说明两套页面各自恢复。
5. 此时 A 尚未在该窗口访问。从主窗口点击 A 的固定网页，原窗口从 B 切回 A，按需恢复 A 的网页、审查、终端及尺寸；主窗口没有新增重复网页。使用返回快捷键可回到原 `?window=A-task=B` 页面。
6. 主窗口的“在新窗口中打开”唤回 B 原窗口，聊天草稿仍保留，网页标签依然为 `?window=B`，没有被另一窗口覆盖。

HTTP 服务记录显示：第一次重启同时请求 A 与 B 页面；第二次重启同时请求两个 B 页面，点击固定标签时才请求 A 页面。这与原生观察到的按需恢复顺序一致。

## 验证与边界

本轮为原生验收，沿用第 172 篇已通过的 173 项相关测试，没有改动源码或重复运行相同测试。构建脚本启动和严格签名检查通过。验收结束关闭本地 HTTP 服务，恢复原数据目录及普通启动参数，确认原任务和既有草稿保留、输入框可聚焦。

“系统允许恢复时自动恢复多个独立窗口”、同任务多窗口布局隔离、固定标签跨任务按需恢复已有原生证据；这并不证明任意系统设置下都应自动重开窗口。跨进程返回/前进历史、网页表单/导航历史和文件编辑器内容状态恢复仍不在本轮范围。完整拖放与所有 Codex 页面配对仍未完成。
