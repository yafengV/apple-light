此前 ShipiOS 每个新监控的首轮都会提前创建工作树。现在没有关联工作树时，模型先在配置检出目录检查；没有修复请求就不创建目录、不运行初始化脚本，下一轮继续检查同一任务。两种协议均提供受当前监控归属约束的 `shipios_request_pr_worktree`。工具先持久保存具体修复原因，明确返回“已请求、尚未创建”；重复调用保留首个原因。模型成功结束检查回合后，应用准备不携带来源修改的隔离检出，在同一任务中继续修复回合。原任务、历史、草稿和主窗口选择不跳转。

Core 的检查回合强制只读；已明确启用的网络权限在检查回合保留，未启用的网络仍受限，普通审查和侧聊的网络策略保持原行为。切换到修复检出或后续普通人工回合时重新建立对应的运行配置，不能沿用检查阶段的只读状态。真实 Core 夹具验证了来源目录的补丁写入被拒绝、修复补丁只写入隔离目录，以及随后人工回合恢复原有写入权限。

失败、取消、中断、暂停、任务归属变化和保存失败不会被当成成功的工作树请求。工作树初始化期间暂停，已创建的检出保留，但不切换任务或启动修复。保存了请求或已经创建检出的进程重启后，恢复同一记录，避免重复创建。来源本身是另一个托管检出时，从其稳定仓库来源创建独立修复检出，保留来源修改。既有监控工作树继续复用，不清理或重置其内容；通用自动化仍保留提前创建和传递来源修改的行为。

检查和修复历史、待审查结果一起保存，修复回合关联其检查回合；记录结果前重新检查监控归属，不能把迟到结果写入替换任务。恢复修复结果不会重复模型请求。工作树准备后模型启动失败保留检出，并恢复原检查任务路径以供重试。
