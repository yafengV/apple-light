# 命名权限档案：主窗口设置与任务菜单

通用设置新增同页的命名权限档案列表和 TOML 编辑器。保存前调用包内 Agent，以固定版本 Codex Core 的严格加载器校验档案；合法定义保存到 ShipiOS 自有的 `workspace.json`，不读取用户个人 Codex 配置。全局默认、新任务草稿、已有任务和弹出首页的权限菜单均可选择档案。任务保存的是所选定义的快照；编辑或删除目录项不会悄悄改变已有任务。设置搜索可定位到新增入口。

Swift 客户端在 `codex.thread.start` 明确传入档案 ID、配置文本与当前基础权限选择。档案变更会重新建立本任务的 Core 会话；切回内置权限会清除活动档案。Agent 续接时按新客户端显式选择更新基础权限及持久记录，旧客户端仍沿用旧记录。命名档案生效时，手动权限子菜单不再把未生效的回退值误标为已选择。

Core 校验结果同时标记可能越出项目范围的档案；这类档案只能在用户开启输入区“完全访问”选项后用于未来任务。关闭该选项会重置未来任务的高权限选择，已有任务继续保留快照。旧数据缺少风险标记时保守地视作高权限，需要重新编辑并保存以更新标记。

验证：49 项权限与设置相关 Swift 回归、14 项 Codex 库测试、15 项 Agent 测试、Rust fmt/Clippy、正式应用构建和严格签名通过。使用 `/private/tmp/shipios-named-permissions-ui-20261001` 的隔离签名应用，原生窗口确认“添加只读档案 → Core 校验保存 → 默认权限选择 → 新任务菜单选择 → 发送任务”；任务私有 `config.toml` 含 `:read-only`，`thread.json` 记录档案 ID。切到仍为只读的内置选项并续接后，`thread.json` 确认 ID 清空、基础沙箱为 `read-only`。设置仍是唯一主窗口的内容页，返回后的输入框可编辑；命名档案生效时手动子菜单无误导性勾选。最后增加的高权限筛选逻辑已通过自动化测试，但 Mac 锁屏阻挡了该版本的前台复查。

本机假服务地址故意不提供模型回复，测试回合随后停止；此结果不能证明真实用户服务或模型执行成功。Codex 参考客户端仍无法由当前桌面控制接口读取，45 项完整双端页面/交互配对仍为 **0/45**，不能称 UI 已完全对齐。
